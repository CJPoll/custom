# The agent-definition preprocessor (`ai/bin/build-agents`)

Athena agent definitions are **generated**, not hand-written. A per-agent
template plus a set of shared blocks are expanded by `ai/bin/build-agents` into
the `.md` file Claude Code actually loads.

```
ai/agents/athena:<Name>.md.in    template  — the agent's own prose + @include lines   (SOURCE)
ai/blocks/**/*.md                blocks    — shared prose, each fact in exactly one place (SOURCE)
ai/blocks/routing.yml            manifest  — which agent MUST carry which block/skill  (SOURCE)
ai/agents/athena:<Name>.md       rendered  — GENERATED, never edit                   (OUTPUT)
```

The rendered file opens with a `<!-- GENERATED by ai/bin/build-agents — DO NOT
EDIT. -->` banner. If you find yourself editing a file with that banner, stop:
edit the `.md.in` or the block, then rebuild.

## Why it exists

Three agents (Architect, Captain, Admiral) share doctrine — the 5-bucket
architecture, the TDD order, access-control rules, the never-end-turn-waiting
rule. Before the preprocessor those paragraphs were copy-pasted and drifted.
Now each fact lives in one block file, and `routing.yml` states which agents
must carry it, so a doctrine change is one edit and one rebuild.

## Directive syntax

Exactly one directive: a line that is nothing but

```
@include <block-path>
```

- `<block-path>` is relative to `ai/blocks/`, without the `.md` extension:
  `@include arch/5-bucket` reads `ai/blocks/arch/5-bucket.md`.
- The regex is line-anchored (`^@include[ \t]+(\S+)[ \t]*$`). Leading
  whitespace, trailing text, or an `@include` embedded mid-line is *not* a
  directive and is copied through verbatim.
- The block's contents replace the line in place (trailing newline trimmed).
  Surround the directive with blank lines in the template so the block's
  heading lands as its own paragraph.
- **Expansion is one level deep.** Blocks are read verbatim; an `@include`
  inside a block is not expanded. Keep blocks flat.
- Frontmatter is passed through untouched. Only the body is scanned.

## What the build enforces (lint)

The build fails, writing nothing, if any of these hold:

| Check | Error |
| --- | --- |
| Template has no / malformed YAML frontmatter | `missing or malformed YAML frontmatter` |
| `@include` names a block with no file | `no such block (ai/blocks/<blk>.md)` |
| Same block included twice in one template | `appears more than once` |
| `routing.yml` lists an agent under a block, template lacks the include | `routing.yml requires @include <blk>` |
| Template includes a block `routing.yml` does not list it for | `not authorized by routing.yml` |
| A block file no agent consumes | `orphan block` |
| `routing.yml` names a block or agent that does not exist | `has no block file` / `lists unknown agent` |
| `routing.yml` lists a preloaded skill the template's `skills:` frontmatter omits | `requires preloaded skill` |

The routing manifest is therefore a *two-way* contract: an include must be both
present in the template and authorized in `routing.yml`. Adding a block to an
agent is always two edits.

## Commands

```
ai/bin/build-agents            expand + lint, write ai/agents/athena:*.md
ai/bin/build-agents --check    lint + verify rendered files are current; writes nothing (use in CI / pre-commit)
ai/bin/build-agents --install  build, then copy rendered .md files to ~/.claude/agents/
```

Run with bare `ruby` — it is deliberately stdlib-only (`yaml`, `set`,
`fileutils`) so it never touches a Bundler environment. `--check` exits
non-zero on a stale render, which is how you detect "someone edited a template
and forgot to rebuild".

On this machine `~/.claude/agents` is a **symlink** to `ai/agents/`, so a
plain build is immediately what Claude Code loads; `--install` is only for a
machine where that symlink is absent (it copies the rendered files into a real
`~/.claude/agents/` directory). Check with `ls -ld ~/.claude/agents` before
assuming either.

## Blocks vs skills vs CLAUDE.md vs template prose

Four places can hold instruction text. They differ in *who* reads them and
*when*.

| Mechanism | Read by | Loaded | Use for |
| --- | --- | --- | --- |
| **Block** (`ai/blocks/**`) | Only the agents `routing.yml` routes it to | Baked into the agent's system prompt at build time — always present, no decision to load | Doctrine two or more agents must carry identically and unconditionally: architecture rules, TDD order, access-control policy, the never-end-turn-waiting rule. |
| **Template prose** (`.md.in` body) | That one agent | Baked in at build time | The agent's identity, inputs, workflow, reporting format — anything true of exactly one agent. |
| **Skill** (`ai/skills/<name>/SKILL.md`) | Any session or agent, on demand | Pulled in when the model decides the task matches the skill description, or when listed in an agent's `skills:` frontmatter for deterministic preload | Procedures that are task-triggered rather than always-on: how to post a standup, how to validate a spec, how to scaffold an agent. Anything with reference material too long to carry in every prompt. |
| **CLAUDE.md** (`~/CLAUDE.md`, `<repo>/CLAUDE.md`) | Every session in scope, main and subagents alike | Injected at session start | Machine- or repo-wide facts and hard rules that apply regardless of which agent is running: identity, memory policy, project layout, hard rules, per-machine automation. |

Decision procedure:

1. Does it apply to every session on this machine / in this repo? →
   **CLAUDE.md**.
2. Is it only needed when a specific kind of task comes up, or is it long
   reference material? → **Skill**. If a particular agent must always have it
   loaded, list it in that agent's `skills:` frontmatter and add the routing
   entry under `skills:` in `routing.yml`.
3. Must two or more agents carry it word-for-word, always? → **Block**, routed
   to exactly those agents.
4. Otherwise it is that one agent's own text → **template prose**.

Two rules of thumb the build encodes:

- A block with one consumer is a smell (the build allows it, but if only one
  agent needs it, it is template prose). A block with zero consumers is an
  error.
- Never restate a block's content in a template or a skill. The point of the
  block is that the fact exists once.

## Workflows

**Change shared doctrine.** Edit `ai/blocks/<path>.md`, run
`ai/bin/build-agents`. Every routed agent picks it up.

**Add a block.** Create `ai/blocks/<area>/<name>.md` (start it with a `##`
heading — it lands inside an agent body). Add `<area>/<name>: [Agent, ...]`
under `blocks:` in `routing.yml`. Add `@include <area>/<name>` to each listed
template. Build.

**Give an existing block to another agent.** Add the agent to the block's list
in `routing.yml` *and* add the `@include` to its template. One without the
other fails the build.

**Add a new athena agent.** Write `ai/agents/athena:<Name>.md.in` (frontmatter
+ prose + any `@include`s), register any includes in `routing.yml`, run
`ai/bin/build-agents`. Do not create the `.md` by hand. Name rules from `SKILL.md` still
apply — the build does not validate `name:`.

**Preload a skill into an agent.** Add the skill to the agent's `skills:`
frontmatter list and to `skills:` in `routing.yml` so the build enforces it.

## Gotchas

- Editing the rendered `.md` is silently lost on the next build. The banner is
  the only guard.
- `--check` compares byte-for-byte, so a template edit that changes nothing
  semantically (trailing whitespace) still reads as stale until rebuilt.
- Template filename → agent name is `athena:<Name>` with the `.md.in`
  stripped; `routing.yml` uses the short `<Name>`. A mismatch shows up as
  `lists unknown agent`.
- Block files are matched by `ai/blocks/**/*.md`; `routing.yml` is the only
  non-`.md` file allowed in there.
